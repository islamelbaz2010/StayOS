## Purpose

This article defines how StayOS makes product decisions: what to build, when, and why. It prevents the most common product mistakes — building features users didn't ask for, building infrastructure without demand, or deferring features that the marketplace actually needs to function.

---

## Background

StayOS made a significant product bet in Sprint 0: build the full platform (FC-01–FC-07) before the first validated transaction. This was a calculated risk. The reasoning: marketplace trust requires identity verification and escrow before any transaction; without these, even manual transactions wouldn't be on the platform.

Going forward, the risk is the opposite: the temptation to continue building (because building is comfortable and measurable) rather than spending time in customer discovery, sales, and operations (which is uncomfortable and hard to quantify).

The framework below is designed to make the right product decision at each stage, based on evidence.

---

## Core Framework: The Four-Gate Test

Before building any feature, run it through four gates:

### Gate 1: Stage Gate — Does This Feature Serve the Current Stage?

StayOS operates in Stage 1 (Ignition Phase). The only features worth building in Stage 1 are features that:
- Enable the first 50 listings to be onboarded
- Enable the first 200 completed bookings
- Protect marketplace trust (identity, escrow, dispute resolution)
- Reduce manual operations burden below what is sustainable

Features that serve Stage 2, 3, or later stages fail Gate 1 regardless of how useful they sound.

**Example**: "We should build dynamic pricing based on demand signals."
Gate 1 check: Dynamic pricing requires historical booking data to calibrate. At Stage 1, we have no historical data. This feature serves Stage 2+. Gate 1 fails → defer.

---

### Gate 2: Evidence Gate — What Evidence Supports Building This?

There are three valid types of evidence:

**Type A: Customer Request (Explicit)**
A host or guest directly stated they need this feature and explained why. Weight: high. Validation: confirm the request is consistent across multiple users, not just one.

**Type B: Operational Bottleneck (Observed)**
The operations team is doing something manually 50+ times per month that could be automated. Weight: high. Validation: count the manual instances; if it's truly 50+/month, the automation has positive ROI.

**Type C: Marketplace Function Requirement (Derived)**
Analysis of the marketplace model shows this feature is required for the marketplace to function (not just to function well). Weight: very high. Validation: test the hypothesis by running the marketplace without it — what breaks?

**Invalid evidence**:
- "Competitors have it" (competitor analysis is useful for inspiration, not for build decisions)
- "It seems like a good idea" (good ideas without customer evidence are bets, not decisions)
- "Users will want it when they see it" (Steve Jobs reasoning; valid for very few decisions)

---

### Gate 3: Cost Gate — What Is the True Cost of Building This?

Costs are almost always underestimated. Before building:

**Engineering cost**: Days of engineering time × average daily loaded cost. Not just the initial build — include testing, code review, deployment, and ongoing maintenance (typically 20% of build cost per year).

**Opportunity cost**: What else could this engineering time build? Is the feature being considered worth more than the alternatives?

**Complexity cost**: Does this feature add to the codebase complexity in a way that makes future features harder to build? (A feature that seems simple but requires restructuring the auth system has a complexity cost far beyond its stated engineering hours.)

**Support cost**: Will this feature generate more support contacts? How many? At what cost?

Decision rule: If the total 12-month cost exceeds the estimated 12-month value generated by the feature, do not build it.

---

### Gate 4: Reversibility Gate — Can We Undo This?

Not all product decisions are equally reversible:

**Highly reversible**: Feature flag, UI change, copy change, API endpoint addition
→ Build and test; rollback if it doesn't work

**Moderately reversible**: Database schema change, new table, modified API contract
→ Requires more careful design; migration path for rollback needed

**Difficult to reverse**: Changing the core escrow model, changing the identity verification provider, changing the payout timing (BR-FIN-01)
→ Requires executive decision; get it right the first time; migration cost of reversal is very high

**Effectively irreversible**: Publishing a public API that external parties depend on, making a commitment to an institutional partner about platform features
→ Do not do these without full conviction; you will live with the consequences

For Gate 4: if the feature is difficult or impossible to reverse, apply 3× the normal evidence threshold before building.

## Build vs. Buy vs. Partner Matrix

For every capability, StayOS has three options: build it internally, buy (integrate) a third-party solution, or partner with a company that provides it as a service.

| Capability | Build | Buy | Partner |
|-----------|-------|-----|---------|
| Identity verification | FC-01 (AWS Textract + Rekognition) | Third-party KYC (Jumio, Onfido) | Verified by government |
| Payment processing | Never | Paymob (primary), Stripe | InstaPay for low value |
| Cleaning management | Manual coordination | Cleaning platform API | Cleaning company partnership |
| Dynamic pricing | Stage 2 internal | AirDNA / Pricelabs API | None |
| Customer support ticketing | WhatsApp (manual) | Zendesk / Freshdesk | None |
| Property photography | In-person team visit | Matterport / professional | Photography agency |

**Build** decisions: When the capability is core to StayOS's competitive differentiation, when cost of third-party is prohibitive, or when the third-party doesn't serve the Egyptian market.

**Buy** decisions: When the capability is not differentiating (payments, support ticketing, analytics), when the third-party solution is mature and well-tested, and when the integration cost is lower than the build cost.

**Partner** decisions: When the capability requires human labor at scale (photography, cleaning), and when a partnership creates mutual incentives.

## Feature Prioritization at Stage 1

At Stage 1, features are prioritized in this order:

**Priority 1 — Trust Infrastructure** (already built in FC-01, FC-03, FC-06, FC-07)
Any gap in trust infrastructure is a blocker. Guests won't book without identity verification. Hosts won't host without payment security. These features have effectively infinite priority until complete.

**Priority 2 — Host Onboarding Speed**
The speed at which a new host goes from signup to first live listing is a critical metric. Any feature that removes friction from host onboarding gets Priority 2 treatment.

**Priority 3 — Operational Sustainability**
Any feature that reduces the manual operations burden (turnover tracking, cleaning dispatch, check-in coordination) to below what the team can handle is Priority 3.

**Priority 4 — Guest Experience Quality**
Features that improve the guest experience after trust is established. Better search, better photos, better communication.

**Priority 5 — Everything Else**
Dynamic pricing, mobile apps, advanced analytics, partner integrations — everything that is valuable but not required for Stage 1 function.

## Common Product Decision Mistakes

**Mistake 1: Building for imaginary users**
"Young Egyptian professionals who use apps for everything" — this is an assumption, not a validated user. Build for the users who have actually signed up and provided feedback.

**Mistake 2: Treating technical debt as optional**
Technical debt in core systems (the database schema, the authentication model, the escrow model) compounds. A shortcut in Sprint 0 becomes a migration project in Sprint 6. Distinguish between acceptable technical debt (non-core shortcuts) and unacceptable technical debt (core system shortcuts).

**Mistake 3: Feature creep disguised as user requests**
"Three users asked for X, so we should build it" — maybe. But: were the three users representative of the broader user base? Was X what they actually needed, or was it what they thought would fix their real problem? User requests are signals, not specifications.

**Mistake 4: Building before the manual process is understood**
Automating a process you haven't done manually means you don't know what you're automating. StayOS's approach: do the first 10 turnovers manually, understand every step, then build the automation. This is also why the first bookings are deliberately manual (Phase 0 validation).

**Mistake 5: Infrastructure before demand**
"We should build multi-tenant database architecture for when we expand to multiple cities." This is engineering for hypothetical future demand that may not materialize. Build what the current demand requires. Refactor when the demand proves out.

## Real-World Scenarios

### Scenario A: A Partner Asks for a Feature
A major hotel chain that StayOS is trying to bring onto the platform says: "We need an API to sync our property management system directly with StayOS inventory. Otherwise we can't join."

**Four-Gate Analysis**:
- Gate 1 (Stage): This serves supply acquisition in Stage 1. Relevant.
- Gate 2 (Evidence): One specific high-value partner's stated requirement. High weight — this is blocking a supply acquisition.
- Gate 3 (Cost): PMS API integration is moderate engineering effort (2–4 weeks). Revenue from this hotel chain: potentially 20+ listings. ROI appears positive.
- Gate 4 (Reversibility): API integration with a specific PMS system. Moderately reversible (can be deprecated if partner churns). Not an architectural lock-in.

**Decision**: Build, but negotiate with the partner: "We'll build this integration within 6 weeks. We need your commitment to onboard [number] properties before we prioritize this."

### Scenario B: An Engineer Proposes a Performance Optimization
Engineer says: "Our spatial search query takes 200ms. I can get it to 50ms with some index optimization."

**Four-Gate Analysis**:
- Gate 1 (Stage): Performance is relevant to Stage 1 only if 200ms is causing user problems. At 10 listings and 50 searches per day, 200ms is not a user-facing problem.
- Gate 2 (Evidence): No user complaints about search speed. No evidence of search abandonment due to latency.
- Gate 3 (Cost): Small engineering effort (1–2 days). Low cost.
- Gate 4 (Reversibility): Index optimization is highly reversible.

**Decision**: Defer. Not because it's a bad idea — it's a fine idea — but because the engineering time would be better spent on Priority 1–3 features. "Add this to the backlog; we'll revisit when we have 100 searches per hour and can measure the actual user impact of 200ms latency."

## Checklist

### Before Building Any New Feature
- [ ] Stage Gate: Does this serve the current stage (Stage 1, Ignition)?
- [ ] Evidence Gate: What evidence supports this? (user request, ops bottleneck, or marketplace requirement)
- [ ] Cost Gate: Total 12-month cost vs. 12-month value estimated?
- [ ] Reversibility Gate: How hard to undo? Is the evidence threshold proportional?
- [ ] Decision logged in `.ai/CURRENT/DECISION_LOG.md` if it's a major decision?
- [ ] Alternatives considered and documented?
